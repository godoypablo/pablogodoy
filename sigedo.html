¿Qué es SIGEDO?

SIGEDO = Sistema Integrado de Gestión Electrónica de Documentos

Es un sistema web especializado para el Tribunal de Cuentas de Entre Ríos (TCER), una institución argentina que audita y controla las cuentas del gobierno provincial.

Propósito principal: Gestionar documentos financieros (rendiciones de cuentas, subsidios, multas), procesarlos a través de múltiples etapas de revisión y auditoría, firmarlos digitalmente y mantener un registro imutable de cada acción para auditoría permanente.

Estados de un Documento (Máquina de Estados)

Un documento pasa por estos estados en orden:

INGRESADO ↓ CARATULADO (se asigna auditor) ↓ EN_AUDITORÍA (auditor revisa) ↓ PENDIENTE_INFORME (se escribe informe) ↓ EN_REVISIÓN_SUPERIOR (jefe revisa) ↓ APROBADO (aprobación de superiores) ↓ PENDIENTE_CERTIFICACIÓN (listo para firmar) ↓ CERTIFICADO (firmado digitalmente) ↓ ARCHIVADO (guardado permanentemente)
💡 Importante: El sistema permite 100+ estados configurables. El admin puede agregar nuevos estados sin tocar código.

Guía Rápida: Iniciar SIGEDO Localmente

Cómo levantar SIGEDO después de volver de vacaciones y encender la PC.

Asegúrate de tener instalado:

Java 11

Verifica: java -version

Maven 3.6+

Verifica: mvn -version

PostgreSQL

Debe estar instalado en el sistema

NetBeans (Opcional)

Si prefieres usar IDE en lugar de terminal

Ver estado actual:
sudo systemctl status postgresql
Si no está corriendo, iniciarlo:
sudo systemctl start postgresql
Verificar que la base de datos existe:
psql -U postgres -l | grep sigedo
Si no existe, crearla:
createdb -U postgres sigedo
Tip: PostgreSQL debe estar corriendo ANTES de iniciar SIGEDO. Si no, obtendrás errores de conexión.

Crea estos dos archivos en web/src/main/resources/:

Archivo 1: jdbc.properties
jdbc.driver=org.postgresql.Driver jdbc.url=jdbc:postgresql://localhost:5432/sigedo jdbc.user=postgres jdbc.password=postgres date.defaultFormat=dd/MM/yyyy
Archivo 2: environment.properties
hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect omision.renditiva=01:00:00 omision.renditiva.diligenciables=02:00:00 omision.renditiva.estados=03:00:00 omision.renditiva.legajos=04:00:00 omision.renditiva.multas=05:00:00 omision.subsidios=06:00:00 alerta.chequeo=07:00:00 cambiar.estado.notificacion.electronica=08:00:00 chequear.usuarios=09:00:00 comision.servicio.generacion=10:00:00 geo.salida.particular=11:00:00 rendicionElectronica.chequeo=12:00:00 cargo.subsidio.siaf=13:00:00
Importante: Los placeholders en environment.properties deben estar en formato HH:mm:ss (ej: 01:00:00, no 1:00 ni true).

Problema Inicial:
⚠️ Si preguntas cada 100ms: "¿Hay firmas nuevas?"

= 36,000 requests por hora
= Servidor muy lento
= Base de datos saturada

Solución: ProcesoLento (Espera Inteligente)
Paso 1: Documento llega a PENDIENTE_CERTIFICACION Paso 2: Sistema espera 120 segundos Paso 3: (Una sola vez) Verifica: "¿Hay firmas pendientes?" Paso 4: Si NO → Espera otros 120 segundos Si SÍ → Notifica al jefe Paso 5: Jefe firma digitalmente Paso 6: Sistema registra firma: - Quién: Carlos García - Cuándo: 2024-07-08 14:30:15 - Con qué: Certificado Digital XYZ - Resultado: PDF oficial generado Paso 7: Estado → CERTIFICADO Paso 8: Organismo recibe notificación
✅ Resultado: 120 segundos × 8 horas = 240 requests/día (en lugar de 288,000)

Ejemplo: Jefe quiere ver "Estado por Auditor"

Lo que ve el Jefe:
Auditor | Asignados | En Auditoría | Completados | Demora Prom ─────────────────┼───────────┼──────────────┼─────────────┼──────────── Juan García | 15 | 8 | 5 | 5.3 días María López | 12 | 6 | 4 | 4.8 días Carlos Martínez | 10 | 5 | 3 | 6.2 días
SQL que corre detrás:
SELECT u.nombre, COUNT(d.id) AS documentos_asignados, COUNT(CASE WHEN d.estado = 'EN_AUDITORIA' THEN 1 END) AS en_auditoria, COUNT(CASE WHEN d.estado = 'CERTIFICADO' THEN 1 END) AS completados, ROUND(AVG(EXTRACT(DAY FROM NOW() - d.fecha_ingreso)), 1) AS demora_promedio FROM DOCUMENTO d JOIN USUARIO u ON d.auditor_id = u.id WHERE d.auditor_id IS NOT NULL GROUP BY u.id, u.nombre ORDER BY demora_promedio DESC

@Service @Transactional public class ServicioDocumentoImpl { @Autowired private DocumentoDAO documentoDAO; public Documento crearDocumento(DocumentoDTO dto) { // Validación if (dto.getTitulo() == null) { throw new IllegalArgumentException("Título requerido"); } // Crear objeto Documento doc = new Documento(); doc.setTitulo(dto.getTitulo()); doc.setMonto(dto.getMonto()); doc.setEstado(TipoEstadoDocumento.INGRESADO); // Guardar documentoDAO.save(doc); // → INSERT en BD // Registrar en auditoría registrarAccion(doc, "Documento creado"); return doc; } }

Patrones Importantes

1. Separación de Capas

Web no habla con BD. Web → Servicios → DAOs → BD
Facilita testing, mantenimiento, reutilización

2. Transacciones (@Transactional)

Si algo falla → deshacer TODO
Evita datos inconsistentes

3. Inyección de Dependencias (@Autowired)

Spring crea objetos automáticamente
Facilita testing con mocks

4. Auditoría Imutable

CADA acción se registra en tabla ACTUACION

En la pantalla "Por Institución", cada rendición tiene un botón para descargar un PDF con todos los datos. Usuarios externos pueden descargar solo sus propias rendiciones.
⏰ Períodos de Rendición:
La maqueta define si es anual, semestral, trimestral, etc. El sistema automáticamente muestra los períodos vigentes según la institución.
🔍 Búsqueda y Filtros:
En "Por Institución" puedes filtrar por: institución, año, período, estado de rendición. Muy útil cuando tienes miles de rendiciones.
📌 Plantillas (Maqueta):
La maqueta es como un "template" reutilizable. Creas una vez y se aplica a todas las instituciones del mismo tipo. Modificarla afecta a todas las futuras rendiciones.
🔐 Seguridad:
Los usuarios externos NUNCA pueden ver rendiciones de otras instituciones, ni modificar configuraciones. Está controlado por el sistema.

Dónde se registra todo

En SIGEDO nada se descubre solo. Al agregar una pantalla, un servicio, un DAO o una entidad en cualquiera de estos cinco circuitos hay que registrarlo a mano en estos archivos, o el arranque falla o el mapeo no existe.

Página nueva — WicketApplication.init(): mountPage(...) para la URL, MetaDataRoleAuthorizationStrategy.authorize(...) para el rol, y paginasParaAnexoRequerimiento.put(...) si es una pantalla de carga de anexo. Los tres lugares, no uno.
Ítem de menú — Template.html (markup), Template.java (link + SecurityUtil.setAuthorization) y Template.properties (texto).
Servicio nuevo — service-impl/src/main/resources/spring-service.xml, id servicio.xxx, inyección por setter. SpringServiceDependencyGraphTest falla si el servicio nuevo entra en el conjunto de ciclos conocidos: hay que romper el ciclo, no ampliar la lista.
DAO nuevo — dao-impl/src/main/resources/spring-dao.xml, id xxx.dao, parent="dao.base".
Entidad nueva — dao-impl/src/main/resources/META-INF/persistence.xml, unidad tcer, como <class>. El escaneo implícito está deshabilitado a propósito; hoy hay 27 entradas del paquete rendicionElectronica. HibernateMappingBootstrapTest lo verifica.
Grilla de búsqueda — una clase EntidadCtrlQuerysXxx en model/…/modelo/entidadBusqueda/, consumida vía servicio.entidadQuerys.
